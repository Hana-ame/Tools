## 2. 编写 zen_proxy_local.py（本地双栈版）
- 基于 zen_proxy.py 改写：
  - 监听 `0.0.0.0:8000`（HTTP 明文，无 TLS）
  - 全 CORS：`Allow-Origin *`、`Allow-Methods` 全方法、`Allow-Headers *`、`Expose-Headers *`、`Max-Age 86400`，OPTIONS 返回 204
  - 保留 v4/v6 上游双会话 + `FreeUsageLimitError` 冷却切换

- 路由：`GET /v1/models` 转发到上游 `/models`；`POST` 一律转发 `/chat/completions`；默认模型 `deepseek-v4-flash-free`，`max_tokens` 上限 65536。
- 测试通过：models 200、chat completion 正常。

## 3. IPv6 探测（无 IPv6 时的处理）
- 新增 `ipv6_available()`：三级检查
  1. `socket.has_ipv6`
  2. `getaddrinfo` 解析 opencode.ai 的 AAAA（AF_INET6）
  3. 真实 TCP 连接测试（3s 超时）
- 探测失败则 `session_v6 = None`，请求循环跳过（`if session is None: continue`）。
- 启动日志打印 `IPv6 upstream: enabled / disabled (no local IPv6)`。
- 本机实测：`has_ipv6=True` 但无真实 IPv6 出口 → 正确探测为 False，纯 v4 运行。

## 5. Push 踩坑与修复（重点）
- 现象：`git push` 被拒（远端有新提交）→ `git pull --rebase` 反复报
  `Your local changes to the following files would be overwritten by merge`，
  且涉及 reports/ 全部 39 个文件，看似是后台进程持续 chmod。

  git 的 filemode 检测认为文件永远被改。

## 6. 错误切换是否无感（对比分析）
用户先问 zen_proxy_local，后澄清问的是 zen_multi.py。

### zen_proxy_local.py（v4/v6 双栈）
- 请求发出前失败（连接/DNS/超时）→ 无感切换，但每失败一次最多拖 10s(connect)/120s(timeout)。
- **流式中途断开 → 有 bug**：会尝试用另一栈给已进入流的客户端发第二个 HTTP 响应，协议损坏。
- 双栈全挂 → 429/503。

### zen_multi.py（bwh / vps / cloudcone 三源）
- `ORDER` 轮转（`_rotate` 每请求递增，起点轮换），支持 `X-Zen-Source` 头 / 模型名后缀强制指定源。
- 请求前失败 → 无感切换；坏源进 60s 短冷却，`FreeUsageLimitError` 冷却到 UTC 午夜。
- **流式中途断开 → `started=True` 后直接 `close_connection=True` 断连**，不会二次响应污染协议（比 local 版好），但客户端看到截断流 = 一次失败，需客户端重试。
- 全源耗尽 → 429（限流）或 503。
- 结论：请求前的失败无感，中途失败任何代理都无法做到无感（SSE 字节收不回）。
